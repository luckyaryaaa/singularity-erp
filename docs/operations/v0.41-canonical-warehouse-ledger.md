# v0.41.0 — Canonical Warehouse Ledger (Stage 1)

**Tanggal:** 29 Juli 2026
**Cakupan blueprint:** §9.8 Inventory and Warehouse (dimensi lokasi kanonik)
**Migration:** 076 `canonical_warehouse_ledger`

## 1. Konteks & keputusan

Blueprint §9.8 menuntut migrasi dari "Branch-as-Warehouse" ke hierarki nyata
**Plant → Warehouse → Storage Location → Bin**. Strukturnya sudah ada sejak 012
(`plants`, `org_warehouses`, `storage_locations`, `warehouse_bins`), tetapi stok
masih menggantung pada cabang: `stock_lots.warehouse_id`, `inventory_balances`,
dan `stock_reservations` semuanya FK ke `branches`.

**Temuan pengukuran:** "gudang = cabang" tertanam di **±197 penggunaan
`warehouse_id` lintas 20 file backend**, dipakai untuk RLS, scope, valuasi,
opname, reservasi, dan produksi. Membalik grain (menjadikan `warehouse_id`
menunjuk `org_warehouses`) adalah **cutover berlapis** yang menyentuh RLS dan
puluhan modul — tidak dapat dilakukan aman dalam satu langkah tanpa meregresi
suite.

**Keputusan:** kerjakan **Stage 1** — tegakkan dimensi gudang kanonik tanpa
membalik kunci isolasi. Cabang tetap kunci scope/RLS; stok memperoleh identitas
gudang nyata; konsistensi dijaga trigger. Jembatan cabang↔gudang menjadi
**eksplisit dan ter-enforce** (menutup temuan audit "◐ masih bridging"). Stage 2
(grain-flip penuh) menjadi cutover tersendiri.

## 2. Perubahan skema (migrasi 076)

| Objek | Keputusan |
|---|---|
| `org_warehouses.is_default` | boolean + partial unique index (maks. satu default/cabang) |
| Backfill default | setiap cabang aktif memperoleh gudang default; cabang tanpa gudang dibuatkan `WH-<code>` (plant di-resolve bila cabang punya satu) |
| `stock_lots.org_warehouse_id` | FK `org_warehouses`, nullable, berindeks |
| Trigger `resolve_stock_lot_warehouse` | BEFORE INSERT/UPDATE self-healing: NULL/lintas-cabang → gudang default cabang |
| View `stock_warehouse_ledger` | security_invoker; Legal Entity → Plant → Warehouse + ringkasan stok dari lot |

## 3. Invariant & perilaku

- **Gudang stok selalu di cabangnya.** Trigger memaksa `org_warehouse_id` berada
  di `warehouse_id` (cabang) lotnya; penempatan spesifik ke gudang lain dalam
  cabang yang sama tetap dihormati, lintas-cabang di-heal ke default.
- **Ledger mengikuti penempatan fisik.** Put-away (058) kini menyetel
  `org_warehouse_id` lot ke gudang rak tujuan — DONE berarti gudang lot benar.
- **Cabang tetap kunci isolasi.** Tidak ada perubahan RLS/scope; nol churn pada
  ±197 titik `warehouse_id`. Inilah yang membuat Stage 1 aman.

## 4. Endpoint & UI

- `GET /api/inventory/warehouses` — ledger gudang kanonik per cabang (delegated
  `inventory.view`, branch-scoped). Authorization matrix: Inventory 20→21,
  total baseline **298 handler**; OpenAPI menambah operasi ber-cookieAuth.
- Tab **Gudang** pada modul Persediaan: daftar gudang dengan plant, tipe, badge
  default, jumlah lot, dan qty; ringkasan Plant→Gudang.

## 6. Stage 2 (belum dikerjakan) — grain-flip penuh

Menjadikan `org_warehouse` sebagai grain stok sebenarnya (menggganti makna
`warehouse_id`, `inventory_balances`, `stock_reservations`, RLS, dan ±197 titik
kode + test fixtures) adalah cutover berlapis tersendiri: introduce → dual-write
→ migrasi query per modul → flip RLS → hapus kolom lama. Direkomendasikan
dieksekusi sebagai wave terjadwal dengan feature flag dan bukti per modul.

## 7. Gate manusia (tidak berubah)

RTO/RPO, offsite proof, dan Owner sign-off tetap fail-closed. Status v0.41.0
adalah engineering release candidate, bukan izin aktivasi produksi.
